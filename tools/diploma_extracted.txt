[Heading1] АНОТАЦІЯ
У дипломній роботі розглянуто розробку інтелектуальної веб-платформи AdoptPet для підтримки процесу адопції тварин із використанням сучасних веб-технологій та методів штучного інтелекту. Проведено аналіз предметної області, існуючих pet-tech платформ, recommendation systems та підходів комп’ютерного зору для задач класифікації порід тварин.
У роботі спроєктовано та реалізовано fullstack-застосунок на основі Next.js, MongoDB Atlas та Auth.js. Система підтримує каталог тварин, пошук і фільтрацію, подання заявок на адопцію, адміністративний функціонал та AI-помічника для персоналізованого підбору тварин.
Окрему увагу приділено розробці ML-модуля для автоматичного визначення породи тварини за зображенням. Для цього використано архітектуру EfficientNet-B3 та бібліотеку PyTorch. Навчання моделей виконувалося на датасетах Stanford Dogs, Oxford-IIIT Pet та Kaggle Dog Breed Identification.
Також реалізовано інтеграцію LangChain та GPT-4o-mini для генерації описів тварин і підтримки взаємодії користувача з платформою природною мовою.
Проведено тестування функціональності системи, інтеграції ML-модуля та процесу контейнеризації із використанням Docker.
Практичне значення роботи полягає у створенні програмного комплексу, який може бути використаний як основа для сучасної цифрової платформи адопції тварин із підтримкою AI-технологій.

ABSTRACT
This thesis presents the development of the intelligent web platform AdoptPet designed to support the pet adoption process using modern web technologies and artificial intelligence methods. The research includes an analysis of the subject area, existing pet-tech platforms, recommendation systems, and computer vision approaches for animal breed classification tasks.
A fullstack application based on Next.js, MongoDB Atlas, and Auth.js was designed and implemented. The system supports an animal catalog, search and filtering functions, adoption applications, administrative functionality, and an AI assistant for personalized pet recommendations.
Special attention is paid to the development of an ML module for automatic animal breed classification from images. EfficientNet-B3 architecture and the PyTorch library were used for this purpose. Model training was performed on the Stanford Dogs, Oxford-IIIT Pet, and Kaggle Dog Breed Identification datasets.
The integration of LangChain and GPT-4o-mini was also implemented for generating pet descriptions and supporting natural language interaction with users.
Testing of the system functionality, ML module integration, and containerization process using Docker was carried out.
The practical significance of the work lies in the creation of a software solution that can serve as a foundation for a modern digital pet adoption platform with AI support.

Однією з предметних областей, у якій потреба в автоматизації є практично значущою, є організація процесу адопції тварин. Традиційна модель взаємодії між користувачами, притулками та волонтерами часто базується на фрагментованих каналах комунікації: соціальних мережах, окремих сайтах притулків, месенджерах або локальних таблицях. Такий підхід ускладнює актуалізацію даних, пошук релевантних анкет, перевірку інформації та супровід заявки на адопцію.
З інженерної точки зору процес адопції тварини можна розглядати як інформаційний workflow, що містить декілька взаємопов’язаних етапів: реєстрацію користувача, пошук тварини, перегляд детальної анкети, аналіз відповідності тварини умовам користувача, подання заявки, обробку заявки адміністратором або волонтером, а також оновлення статусу тварини. Якщо цей процес реалізований без централізованої інформаційної системи, виникають типові проблеми: дублювання даних, неактуальні анкети, відсутність єдиної історії взаємодії, високе ручне навантаження на волонтерів та недостатній рівень персоналізації для кінцевого користувача.
Актуальність розробки платформи AdoptPet полягає у необхідності створення програмного комплексу, який не лише зберігає інформацію про тварин, а й підтримує прийняття рішень під час вибору. На відміну від класичного каталогу, інтелектуальна платформа повинна виконувати роль decision-support system: аналізувати характеристики користувача, співвідносити їх із параметрами тварин, надавати рекомендації та доповнювати неповні дані за допомогою моделей комп’ютерного зору. Саме тому в межах роботи передбачено інтеграцію двох інтелектуальних компонентів: AI-помічника для персоналізованого підбору тварин та ML-модуля для класифікації порід за зображенням.
Розроблений програмний комплекс базується на fullstack-архітектурі з використанням Next.js. Такий підхід дозволяє об’єднати клієнтську частину, серверну логіку, маршрутизацію, обробку форм та інтеграцію з базою даних у межах єдиного технологічного середовища. Для зберігання даних використовується MongoDB Atlas, що відповідає природі предметної області, оскільки анкети тварин можуть мати гнучку структуру та різну кількість атрибутів. Для автентифікації та контролю доступу застосовується Auth.js. Для AI-рекомендацій використовується підхід на основі LangChain/OpenAI, а для класифікації порід - окремий FastAPI-сервіс із моделями глибокого навчання.
Об’єктом дослідження є процес інформаційної підтримки адопції тварин у цифровому середовищі.
Предметом дослідження є архітектурні, алгоритмічні та програмні засоби реалізації веб-платформи з інтелектуальними модулями рекомендацій і комп’ютерного зору.
Метою роботи є розробка, дослідження та тестування програмного комплексу AdoptPet, який забезпечує цифрову підтримку процесу адопції тварин, включаючи каталогізацію анкет, подання заявок, адміністративне керування, AI-рекомендації та автоматичне визначення породи тварини за зображенням.

[Heading1] РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ОБҐРУНТУВАННЯ СТАРТАП-ПРОЄКТУ
[Heading2] 1.1 Аналіз галузі та актуальність теми
Проблема безпритульних тварин є однією з найбільш актуальних соціальних, екологічних та гуманітарних проблем сучасної України. Зростання кількості бездомних собак і котів у містах створює комплекс негативних наслідків: погіршення санітарно-епідеміологічної ситуації, збільшення кількості нападів тварин на людей, перевантаження притулків, фінансові витрати місцевих бюджетів та погіршення умов життя самих тварин. Особливої актуальності ця проблема набула в умовах війни, економічної нестабільності та масового переміщення населення.
За даними українських досліджень, Україна входить до десятки країн світу з найбільшою кількістю безпритульних тварин. Зокрема, за інформацією українських медіа та експертів у сфері захисту тварин, кількість безпритульних собак в Україні може перевищувати 500 тисяч особин, а точна кількість бездомних котів навіть не піддається оцінці через відсутність централізованої системи обліку.
Важливою особливістю галузі є те, що проблема безпритульності тварин має системний характер. Основною причиною появи бездомних тварин є саме діяльність людини: безконтрольне розведення, відмова від домашніх тварин, відсутність культури стерилізації та неналежний рівень відповідальності власників. У policy brief «Безпритульні тварини: вбити неможливо прихистити?» зазначено, що близько 74% безпритульних тварин в Україні є спадково безпритульними, тобто народженими вже на вулиці. Лише невелика частина є загубленими або покинутими власниками.
У дослідженні також наголошується, що в Україні довгий час основним способом регулювання чисельності безпритульних тварин була евтаназія, яка не вирішувала проблему комплексно, оскільки не зупиняла процес подальшого розмноження тварин. Це призвело до формування значної кількості колоній безпритульних тварин у містах та селищах.
Рис. 1.1. Джерела походження безпритульних собак та котів в Україні
«Джерела походження безпритульних собак та котів в Україні» (рисунок 1.1) демонструє співвідношення загублених, покинутих та спадково безпритульних тварин.
Ще однією важливою проблемою є відсутність єдиної державної системи реєстрації та моніторингу тварин. У документі зазначено, що в Україні не ведеться офіційний загальнонаціональний облік безпритульних тварин, а окремі міста здійснюють підрахунок самостійно. Через це державні та муніципальні органи не мають достатньо точних даних для прогнозування та ефективного управління ситуацією.
Рис. 1.2. Карта України з кількістю безпритульних тварин у різних містах
На карті видно значну концентрацію бездомних тварин у великих містах України.
Проблематика безпритульних тварин значно ускладнилася після початку повномасштабної війни. У науковій статті про проблеми безпритульних тварин в умовах війни зазначається, що евакуація населення, руйнування житла та економічні труднощі призвели до збільшення кількості покинутих домашніх тварин. Частина притулків була зруйнована або втратила можливість функціонувати, а волонтерські організації зіткнулися з нестачею фінансування та ресурсів.
Крім гуманітарного аспекту, проблема має також економічну складову. Утримання тварин у притулках, стерилізація, вакцинація та ветеринарне обслуговування потребують значних фінансових витрат. Водночас традиційні підходи до роботи притулків в Україні часто залишаються малоефективними через низький рівень автоматизації процесів. Більшість українських притулків використовують соціальні мережі або окремі сайти для публікації інформації про тварин, однак ці рішення не забезпечують централізованого пошуку, сучасної аналітики та автоматизації процесу адопції.
Аналіз сучасних тенденцій показує, що у світі активно розвиваються цифрові платформи для адопції тварин. Основними трендами галузі є:
створення єдиних електронних баз тварин;
автоматизована ідентифікація тварин;
використання мікрочіпування та цифрових паспортів;
інтеграція систем геолокації;
використання AI та комп’ютерного зору;
персоналізовані рекомендації для потенційних власників;
цифровізація роботи притулків та ветеринарних центрів.
У policy brief також зазначається, що в країнах Європи ефективними виявилися комплексні підходи: реєстрація тварин, обов’язкова стерилізація, створення притулків та центрів адопції, ліцензування розведення тварин і централізовані бази даних.
Особливо перспективним напрямом є використання технологій штучного інтелекту. Сучасні системи комп’ютерного зору дозволяють автоматично визначати породу тварини за фотографією, аналізувати стан тварини та спрощувати процес пошуку нового власника. Це є актуальним для великих платформ адопції, де щоденно обробляються сотні фотографій тварин.
Саме тому актуальним є створення інтелектуальної вебплатформи для адопції та ідентифікації тварин, яка поєднуватиме:
систему пошуку та адопції тварин;
автоматичне визначення породи за фото;
централізовану базу даних;
цифровий профіль тварини;
аналітичні модулі;
інтеграцію з притулками та волонтерськими організаціями.
Для даної дипломної роботи актуальність теми полягає у поєднанні двох важливих напрямів: цифровізації сфери захисту тварин та використання методів штучного інтелекту для автоматизації процесів роботи з тваринами. Розроблювана система дозволить не лише спростити процес адопції, але й підвищити ефективність роботи притулків, покращити ідентифікацію тварин та сприяти гуманному вирішенню проблеми безпритульності.
[Heading2] 1.2 Огляд наукових джерел та існуючих рішень
Сфера цифрової підтримки адопції тварин поступово трансформується від простих інформаційних каталогів до інтелектуальних платформ, здатних автоматизувати пошук, аналіз характеристик тварин та персоналізацію рекомендацій. Такий розвиток став можливим завдяки поширенню технологій штучного інтелекту, комп’ютерного зору та сучасних рекомендаційних систем.
Аналіз існуючих платформ у сфері адопції тварин показує, що більшість з них виконують переважно інформаційну функцію. Такі рішення, як Happy Paw, Club4Paws, DogCat та Patron.center, надають користувачам можливість переглядати анкети тварин, здійснювати пошук за базовими параметрами, публікувати оголошення або підтримувати притулки. Проте ці системи не забезпечують достатнього рівня автоматизації та персоналізації. Зокрема, відсутні інструменти інтелектуального підбору тварин відповідно до характеристик користувача, а також механізми автоматичного аналізу даних, що знижує ефективність процесу адопції.
Разом з розвитком прикладних рішень значний прогрес відбувся у науковій сфері, зокрема у галузі комп’ютерного зору. У роботі Dosovitskiy et al. (2020) запропоновано підхід Vision Transformer, який продемонстрував високу ефективність у задачах класифікації зображень. У дослідженнях Tan та Le (2019) представлено архітектуру EfficientNet, яка забезпечує оптимальне співвідношення між точністю та обчислювальною складністю. Крім того, сучасні дослідження, присвячені класифікації порід тварин (Karthik et al., 2024), підтверджують можливість досягнення точності понад 90% при використанні методів transfer learning на датасетах, таких як Stanford Dogs та Oxford-IIIT Pet.

Якщо моделі VGG забезпечували високу якість за рахунок значної кількості параметрів, то сучасні архітектури EfficientNet досягають кращих результатів при значно меншій обчислювальній складності.
Окрім задач класифікації зображень, важливим напрямом є розвиток рекомендаційних систем, які використовуються для персоналізації сервісів. У роботі Zhang et al. (2021) показано, що використання глибокого навчання у рекомендаційних системах дозволяє враховувати складні залежності між характеристиками користувачів і об’єктів, що значно підвищує точність рекомендацій. У дослідженні Aggarwal (2020) розглянуто сучасні підходи до побудови рекомендаційних систем, включаючи content-based, collaborative та гібридні моделі.
Рис. 1.3. Структура рекомендаційної системи
У контексті платформи для адопції тварин рекомендаційна система може аналізувати такі параметри, як спосіб життя користувача, житлові умови, наявність дітей або досвід утримання тварин, і на основі цього формувати персоналізовані пропозиції. Як показано на рисунку 1.4, така система базується на обробці вхідних параметрів користувача та формуванні списку релевантних рекомендацій. Це дозволяє не лише покращити користувацький досвід, але й зменшити ризик невдалого підбору тварини.
Окрему увагу в сучасних дослідженнях приділяють інтерпретованості моделей машинного навчання. У роботі Lundberg та Lee (2017) представлено метод SHAP, який дозволяє оцінити вплив окремих ознак на результат моделі. Аналогічно, метод LIME (Ribeiro et al., 2016) забезпечує локальну інтерпретацію результатів. Використання таких підходів є важливим для підвищення довіри користувачів до інтелектуальних систем.
З технічної точки зору, сучасні веб-застосунки все частіше реалізуються із використанням fullstack-підходу, що поєднує клієнтську та серверну логіку в межах єдиного програмного середовища. У межах даної роботи використовується фреймворк Next.js, який дозволяє ефективно реалізувати як інтерфейс користувача, так і серверну логіку взаємодії з даними.
Для зберігання інформації використовується хмарна база даних MongoDB Atlas, яка забезпечує гнучку роботу з напівструктурованими даними, такими як анкети тварин, характеристики користувачів та результати рекомендацій. Використання NoSQL-підходу є доцільним у даній предметній області через різноманітність структури даних.
Важливим напрямом розвитку є також інтеграція інтелектуальних модулів у веб-застосунки. У роботі Zhao et al. (2023) показано ефективність використання мовних моделей у побудові інтелектуальних асистентів. У даній системі для реалізації AI-помічника використовується підхід на основі LangChain, який дозволяє обробляти запити користувачів, інтерпретувати введені характеристики та формувати персоналізовані рекомендації. Такий підхід поєднує можливості рекомендаційних систем і сучасних мовних моделей, забезпечуючи більш гнучку та природну взаємодію з користувачем.
Аналіз сучасних pet-tech платформ свідчить про поступовий перехід від статичних інформаційних сервісів до інтелектуальних систем підтримки прийняття рішень. Основними трендами є інтеграція recommendation systems, conversational AI, автоматичного аналізу зображень та персоналізованих алгоритмів підбору. Це дозволяє не лише покращити користувацький досвід, але й оптимізувати роботу притулків та волонтерських організацій.
Аналіз наукових джерел та існуючих рішень показує, що сучасні технології штучного інтелекту створюють передумови для розробки інтелектуальних платформ нового покоління. Поєднання методів комп’ютерного зору, рекомендаційних систем та сучасних веб-технологій дозволяє створити комплексне рішення, яке не лише автоматизує процес адопції тварин, але й підвищує його ефективність за рахунок персоналізації та аналізу даних. Це обґрунтовує доцільність інтеграції AI-помічника у платформу AdoptPet.
[Heading2] 1.3 Аналіз цільового ринку
Аналіз цільового ринку є важливим етапом при розробці цифрового продукту, оскільки дозволяє визначити потенційних користувачів системи, їх потреби, поведінкові характеристики та можливості взаємодії з платформою. У межах даної роботи розглядається аудиторія, яка зацікавлена в адопції тварин, включаючи як українських користувачів, так і міжнародну спільноту.
З демографічної точки зору цільову аудиторію можна умовно поділити на кілька основних груп. Найбільш активною є молодь віком від 18 до 27 років, яка схильна до використання цифрових технологій та підтримує ідею адопції тварин замість їх купівлі. Друга група — це люди віком від 27 до 55 років, переважно сім’ї з дітьми, які шукають домашнього улюбленця та розглядають це як спосіб формування відповідальності у дітей. Окрему категорію становлять користувачі віком понад 55 років, які прагнуть знайти тварину для емоційної підтримки та спілкування.
З географічної точки зору найбільша концентрація цільової аудиторії спостерігається у великих містах України, таких як Київ, Львів, Харків та інші, де зосереджена значна кількість притулків та волонтерських організацій. Водночас важливу роль відіграють прифронтові регіони, де актуальними є питання евакуації та тимчасового догляду за тваринами. Сільська місцевість також є частиною ринку, оскільки притулки часто розташовані за межами міст. Окрім цього, значну частину аудиторії становлять іноземні користувачі, які готові брати тварин з українських притулків, що створює додаткові можливості для розвитку платформи на міжнародному рівні.
Поведінкові характеристики користувачів визначаються їх мотивацією та каналами комунікації. Основними мотивами є етичні переконання, пов’язані з відмовою від купівлі тварин, бажання допомогти тваринам, постраждалим внаслідок війни, а також прагнення знайти емоційного компаньйона. Важливу роль відіграють соціальні мережі, які є основними каналами поширення інформації про адопцію тварин та взаємодії з притулками.
Для більш детального розуміння потреб користувачів було сформовано типові портрети користувачів (User Personas), що дозволяють врахувати різні сценарії використання платформи.

Аналіз ринку також передбачає оцінку його обсягу та потенціалу розвитку. Для цього використовується підхід TAM, SAM та SOM, який дозволяє визначити загальний обсяг ринку, доступну його частину та реалістичну частку, яку може зайняти продукт. Оцінка ринку є орієнтовною та базується на відкритих статистичних даних щодо кількості домашніх і безпритульних тварин в Україні, а також середніх витрат, пов’язаних із процесом адопції.
Загальний обсяг ринку (TAM – Total Addressable Market) включає всіх потенційних користувачів послуг адопції тварин в Україні та за її межами. За оцінками, в Україні налічується близько 5 мільйонів домашніх тварин, з яких приблизно 20% є безпритульними, що становить близько 1 мільйона. При цьому щорічно прилаштовується близько 50 тисяч тварин. З урахуванням середніх витрат на адопцію на рівні 1500 грн, загальний обсяг ринку становить приблизно 75 млн грн на рік.
Доступний ринок (SAM – Serviceable Available Market) визначається як частина TAM, яку може охопити платформа AdoptPet з урахуванням її функціональних можливостей та географічного охоплення. До нього входять користувачі з України, а також міжнародна аудиторія, зацікавлена у адопції тварин. З урахуванням оцінок, доступний ринок становить близько 82.5 млн грн на рік, що включає як внутрішні, так і міжнародні адопції.
Реально досяжний ринок (SOM – Serviceable Obtainable Market) визначає частку ринку, яку платформа може зайняти в короткостроковій перспективі. З урахуванням конкуренції та обмежених ресурсів на початковому етапі, очікується, що платформа зможе зайняти близько 20% ринку протягом першого року, що становить приблизно 16.5 млн грн. У перспективі трьох років цей показник може зрости до 30% за рахунок масштабування платформи та встановлення партнерських відносин.
Досягнення зазначених показників можливе за умови реалізації ефективної стратегії розвитку, яка включає співпрацю з притулками, інтеграцію з ветеринарними клініками, а також впровадження моделей монетизації, таких як преміум-функції або комісія за успішну адопцію. Важливу роль також відіграє маркетинг, орієнтований на активну цифрову аудиторію, зокрема користувачів віком 18–30 років.
Таким чином, проведений аналіз цільового ринку свідчить про наявність значного потенціалу для впровадження інтелектуальної платформи у сфері адопції тварин. Поєднання соціальної значущості, зростаючого попиту та можливостей цифрових технологій створює сприятливі умови для розвитку стартап-проєкту AdoptPet.

Цінність платформи для користувача полягає у зменшенні складності вибору, економії часу та підвищенні ймовірності успішної адопції. Завдяки використанню інтелектуальних алгоритмів система аналізує параметри користувача, такі як спосіб життя, умови проживання та досвід взаємодії з тваринами, і формує рекомендації, що відповідають цим характеристикам. Це дозволяє перейти від пасивного перегляду інформації до активної підтримки прийняття рішень.
З точки зору притулків та волонтерських організацій, платформа створює операційну та інформаційну цінність за рахунок автоматизації процесів розміщення інформації, взаємодії з користувачами та обробки заявок. Це дозволяє зменшити навантаження на персонал та підвищити ефективність прилаштування тварин.
Бізнес-модель платформи AdoptPet базується на поєднанні соціальної місії та комерційних механізмів монетизації. Основними джерелами доходу можуть бути преміум-функції для користувачів, зокрема розширені можливості пошуку, пріоритетне відображення анкет тварин або доступ до перевірених пропозицій. Додатковим джерелом доходу можуть виступати партнерські програми з ветеринарними клініками, зоомагазинами та іншими учасниками ринку pet-care.

Використання сучасних веб-технологій, зокрема fullstack-підходу на основі Next.js, хмарної бази даних MongoDB Atlas та інтеграції AI-помічника на базі LangChain, дозволяє забезпечити гнучкість системи та можливість її розширення на міжнародні ринки. Це створює передумови для розвитку платформи як стартапу з потенціалом залучення інвестицій.
Таким чином, запропонована бізнес-модель поєднує соціальну значущість із економічною доцільністю, а ціннісна пропозиція платформи полягає у використанні інтелектуальних технологій для підвищення ефективності процесу адопції тварин. Це дозволяє створити конкурентоспроможний продукт, орієнтований на потреби сучасного користувача та тенденції розвитку цифрових сервісів.

[Heading2] 1.5. Визначення вимог до продукту
Визначення вимог до програмного забезпечення є ключовим етапом розробки, оскільки дозволяє формалізувати функціональні та нефункціональні характеристики системи, а також узгодити очікування користувачів із можливостями реалізації. У межах даної роботи для опису вимог використано підхід User Stories, який дозволяє представити функціональність системи з точки зору кінцевого користувача, а також метод MoSCoW для їх пріоритизації.
User Stories описують взаємодію користувача із системою у форматі «як [тип користувача], я хочу [дія], щоб [результат]». Такий підхід дозволяє сфокусуватися на цінності функціоналу та забезпечити орієнтацію на потреби користувача.
Для платформи AdoptPet було визначено ключові сценарії використання, пов’язані з пошуком тварин, взаємодією з притулками та використанням AI-помічника.
Для опису функціональних вимог системи використано підхід User Stories, який дозволяє формалізувати потреби користувачів у форматі сценаріїв взаємодії із системою. У межах платформи AdoptPet User Stories охоплюють процеси пошуку тварин, взаємодії з притулками, подачі заявок та використання AI-помічника.
Прикладами User Stories є:
«Як користувач, я хочу фільтрувати тварин за параметрами, щоб швидше знайти потрібну»;
«Як волонтер, я хочу додавати нових тварин у систему, щоб швидше знайти їм дім»;
«Як користувач, я хочу отримувати рекомендації від AI-помічника, щоб обрати тварину відповідно до мого способу життя».
Повний перелік User Stories наведено у додатку 1.
Для визначення пріоритетності функціоналу було застосовано метод MoSCoW, який дозволяє розподілити вимоги на чотири категорії: обов’язкові (Must have), бажані (Should have), додаткові (Could have) та необов’язкові на поточному етапі (Won’t have).
У категорію Must have увійшли вимоги, без яких система не може виконувати свою основну функцію. Реєстрація та авторизація користувачів; перегляд списку тварин; фільтрація; профіль тварини; подача заявки; базовий AI-помічник.
До категорії Should have, тобто бажаних аспектів, які покращують досвід користування, але не є критичними, належать: рекомендації на основі AI; повідомлення про статус заявки; історія взаємодії.
Категорія Could have містить функціональність, яка може бути реалізована за наявності додаткового часу. Рейтинг притулків; відгуки; розширені фільтри.
Категорія Won’t have включає можливості, які свідомо не реалізуються на поточному етапі. До таких належить автоматизоване прийняття рішень щодо схвалення адопції без участі людини, а також складні predictive ML-моделі аналізу поведінки тварин .

[Heading2] 1.6 Обґрунтування необхідності інтелектуального модуля
Як було показано у підрозділі 1.1, однією з ключових проблем у сфері адопції тварин є складність процесу вибору домашнього улюбленця та фрагментованість інформації про тварин. Користувачі змушені самостійно аналізувати велику кількість анкет, враховувати різноманітні фактори, такі як умови проживання, спосіб життя, наявність дітей, досвід утримання тварин, а також особливості характеру та потреб конкретної тварини. У більшості випадків такий вибір здійснюється інтуїтивно або на основі візуальних характеристик, що підвищує ризик невдалого підбору та повторного повернення тварини до притулку.
Традиційні підходи до реалізації подібних систем базуються на використанні баз даних із можливістю фільтрації за заданими параметрами. Проте такий підхід має низку суттєвих обмежень. По-перше, фільтрація передбачає жорстко задані критерії, які не враховують складні взаємозв’язки між характеристиками користувача та тварини. По-друге, користувач повинен самостійно формулювати запит і обирати параметри, що ускладнює взаємодію із системою, особливо для користувачів із низьким рівнем технічної підготовки. По-третє, база даних не здатна адаптуватися до індивідуальних потреб користувача або навчатися на основі попереднього досвіду.
У зв’язку з цим виникає необхідність використання інтелектуального модуля, який дозволяє перейти від статичного пошуку до динамічного формування рекомендацій. Використання методів машинного навчання та інтелектуальних алгоритмів дає змогу враховувати багатокритеріальні залежності між параметрами та забезпечувати більш точний і персоналізований підбір тварин.
У межах даної роботи інтелектуальний модуль реалізується у вигляді AI-помічника, інтегрованого у веб-платформу AdoptPet. Модуль використовує мовні моделі та механізми orchestration на базі LangChain для аналізу характеристик користувача, інтерпретації текстових запитів та формування персоналізованих рекомендацій щодо адопції тварин.
На відміну від традиційних систем фільтрації, інтелектуальний модуль здатний враховувати контекст запиту користувача, працювати з природною мовою та адаптувати рекомендації відповідно до індивідуальних потреб.
Крім того, інтелектуальний модуль може бути використаний для задач комп’ютерного зору, зокрема визначення породи тварини за зображенням. Це є важливим у випадках, коли інформація про тварину є неповною або відсутня.
Рисунок 1.7 Порівняння традиційного пошуку та AI-підбору тварин
Інтеграція інтелектуального модуля у веб-застосунок реалізується в межах fullstack-архітектури на основі Next.js із використанням хмарної бази даних MongoDB Atlas. AI-помічник взаємодіє із серверною частиною застосунку та забезпечує обробку запитів користувачів, що дозволяє створити єдину інтегровану систему без необхідності складної зовнішньої інфраструктури.
Таким чином, використання інтелектуального модуля є обґрунтованим та необхідним для вирішення задач, визначених у даній роботі. На відміну від традиційних підходів, що базуються на статичному пошуку, AI-помічник забезпечує персоналізацію, адаптивність та підвищення ефективності процесу адопції тварин. Це дозволяє не лише покращити користувацький досвід, але й зменшити кількість невдалих адопцій та сприяти більш відповідальному вибору домашніх улюбленців.

У першому розділі було проведено аналіз предметної області адопції тварин та обґрунтовано актуальність розробки платформи AdoptPet. Встановлено, що проблема безпритульних тварин в Україні залишається актуальною, а більшість існуючих цифрових рішень не забезпечують достатнього рівня автоматизації та персоналізації процесу адопції.
У результаті аналізу наукових джерел та існуючих платформ визначено доцільність використання сучасних підходів штучного інтелекту, зокрема рекомендаційних систем, мовних моделей і методів комп’ютерного зору. Використання таких технологій дозволяє створити інтелектуальний сервіс, який не лише забезпечує зберігання та обробку інформації про тварин, але й підтримує користувача у процесі прийняття рішень.
Обґрунтовано необхідність інтеграції інтелектуального модуля, оскільки традиційні підходи на основі баз даних і статичних фільтрів не забезпечують достатньої адаптивності та якості рекомендацій.
Отже, результати першого розділу підтверджують доцільність розробки платформи AdoptPet з інтегрованим AI-помічником та формують основу для подальшого проєктування архітектури системи, реалізації програмного забезпечення та розробки інтелектуального модуля у наступних розділах дипломної роботи.
[Heading1] РОЗДІЛ 2. ПРОЄКТУВАННЯ АРХІТЕКТУРИ ТА ТЕХНІЧНЕ ЗАВДАННЯ
[Heading2] 2.1 Вибір архітектурного стилю та стратегія масштабування
При проєктуванні програмного комплексу AdoptPet важливим етапом є вибір архітектурного стилю, який визначає структуру системи, принципи взаємодії її компонентів та можливості подальшого масштабування. У межах даної роботи було проаналізовано основні підходи до побудови веб-застосунків, зокрема монолітну архітектуру, клієнт-серверну модель та мікросервісний підхід.
Монолітна архітектура передбачає реалізацію всіх компонентів системи (інтерфейс, бізнес-логіка, база даних) у межах єдиного застосунку. Перевагами такого підходу є простота розробки та розгортання, однак він має суттєві обмеження щодо масштабованості та гнучкості. При зростанні навантаження або необхідності розширення функціоналу система стає складною у підтримці та модернізації.
Клієнт-серверна архітектура базується на розподілі системи на клієнтську частину, яка відповідає за взаємодію з користувачем, та серверну частину, що забезпечує обробку даних і виконання бізнес-логіки. Даний підхід є найбільш поширеним у сучасних веб-застосунках, оскільки дозволяє досягти балансу між продуктивністю, масштабованістю та складністю реалізації.
Мікросервісна архітектура передбачає розподіл системи на незалежні сервіси, кожен із яких виконує окрему функцію (наприклад, обробка користувачів, рекомендації, чат, платежі). Такий підхід забезпечує високу масштабованість і гнучкість, однак потребує складної інфраструктури, додаткових витрат на розгортання та підтримку, а також використання інструментів оркестрації.

Рисунок 2.1 Модульно-аналітична схема системи AdoptPet
Даний підхід дозволяє поєднати клієнтську та серверну логіку в межах єдиного програмного середовища, що значно спрощує розробку та підтримку системи. Використання App Router та Server Actions забезпечує ефективну взаємодію між інтерфейсом користувача та серверною частиною без необхідності створення окремого backend-сервісу.
Основними причинами вибору даного підходу є:
масштабованість – можливість розширення функціоналу системи без суттєвих змін архітектури, зокрема інтеграції інтелектуального модуля;
продуктивність – використання серверного рендерингу (SSR) та статичної генерації (SSG) для оптимізації швидкості завантаження сторінок;
простота підтримки – єдина кодова база зменшує складність розробки та кількість помилок;
гнучкість інтеграції – можливість взаємодії з зовнішніми сервісами, зокрема AI-модулем на базі LangChain.
Використання мікросервісної архітектури на даному етапі є недоцільним, оскільки це призведе до ускладнення інфраструктури та збільшення витрат на розробку і підтримку. У той же час монолітний підхід не забезпечує достатньої гнучкості для інтеграції сучасних технологій та масштабування системи.
Для забезпечення безпеки доступу до системи використовується механізм автентифікації NextAuth.js та захищене зберігання змінних середовища.
[Heading3] Стратегія масштабування системи
З урахуванням перспектив розвитку платформи AdoptPet особлива увага приділяється забезпеченню масштабованості та стабільності роботи системи при зростанні кількості користувачів і обсягу даних.
Масштабування системи реалізується за двома основними напрямами: горизонтальним та вертикальним.
Горизонтальне масштабування передбачає розподіл навантаження між декількома обчислювальними ресурсами. У даному проєкті це реалізується за рахунок використання serverless-архітектури на платформі Vercel, яка автоматично створює додаткові екземпляри серверних функцій при збільшенні навантаження. Це дозволяє забезпечити стабільну роботу системи навіть при значному зростанні кількості запитів.
База даних MongoDB Atlas також підтримує горизонтальне масштабування за рахунок механізму шардінгу, що дозволяє розподіляти дані між кількома серверами. Це є важливим для обробки великих обсягів інформації, зокрема анкет тварин, користувачів та результатів рекомендацій.
Вертикальне масштабування передбачає підвищення продуктивності за рахунок збільшення ресурсів серверів. У даному випадку це реалізується через налаштування параметрів MongoDB Atlas та оптимізацію обробки запитів у Server Actions.
Окрім цього, важливу роль відіграє оптимізація продуктивності системи, яка досягається за рахунок:
використання кешування даних (можливе впровадження Redis);
мінімізації кількості HTTP-запитів;
оптимізації запитів до бази даних;
використання статичної генерації для сторінок із незмінним контентом.
Інтелектуальний модуль, реалізований за допомогою LangChain, інтегрується у систему як окремий логічний компонент, що дозволяє масштабувати його незалежно від основного застосунку у разі зростання навантаження.
[Heading2] 2.2 Проєктування компонентів системи (UML)
Проєктування компонентів системи є важливим етапом розробки програмного комплексу, оскільки дозволяє формалізувати структуру застосунку, визначити основні модулі та встановити зв’язки між ними. У межах даної роботи для опису високорівневої структури платформи AdoptPet використано UML-підхід, який дає змогу представити систему як сукупність взаємопов’язаних компонентів, кожен із яких виконує окрему функціональну роль.
З урахуванням обраної архітектури, платформа AdoptPet реалізується як fullstack-застосунок на основі Next.js, у межах якого клієнтська та серверна частини тісно інтегровані між собою. На високому рівні система складається з чотирьох основних компонентів: клієнтського інтерфейсу, серверної логіки, бази даних та зовнішніх API. Їх взаємодія забезпечує повний цикл роботи користувача із системою — від перегляду інформації про тварин до подання заявки на адопцію та отримання рекомендацій.
Рис. 2.2. UML-діаграма компонентів системи AdoptPet
Як показано на рисунку 2.2, центральним елементом системи є клієнтський компонент, який представлений веб-інтерфейсом, доступним через браузер або мобільний пристрій. Клієнтська частина реалізована засобами Next.js та React і відповідає за відображення сторінок, взаємодію з користувачем, введення даних та ініціювання запитів до серверної частини. Саме через цей компонент користувач здійснює пошук тварин, переглядає анкети, заповнює форми та взаємодіє з функціоналом платформи.
Серверний компонент реалізовано засобами Next.js Server. Для цього використовуються Server Actions, API Routes та Node.js-логіка. Автентифікація користувачів забезпечується за допомогою Auth.js. Цей компонент відповідає за обробку запитів, виконання бізнес-логіки, перевірку прав доступу, обробку форм, збереження та отримання даних із бази даних. Завдяки використанню Server Actions значна частина серверної логіки інтегрується безпосередньо у fullstack-середовище Next.js, що дозволяє зменшити кількість проміжних API-викликів та спростити підтримку системи.
Окремим компонентом є зовнішні API, які розширюють функціональні можливості платформи. У поточній архітектурі прикладом такого компонента є Google Maps API, що використовується для роботи з географічними даними, відображення локацій притулків та потенційного пошуку об’єктів поблизу користувача. Інтеграція зовнішніх сервісів дозволяє зробити платформу більш зручною та функціонально насиченою без потреби реалізовувати відповідну логіку з нуля.
Ключовим компонентом системи є база даних MongoDB, у якій зберігається основна предметна інформація. У межах розробленої моделі даних передбачено кілька основних колекцій. Колекція pets містить відомості про тварин, зокрема фотографії, опис, стан здоров’я та інші характеристики, що використовуються в анкеті. Колекція users призначена для зберігання даних користувачів, включаючи облікову інформацію та ролі у системі. Колекція applications використовується для зберігання заявок на адопцію, що дозволяє фіксувати історію взаємодії між користувачами та платформою. Така структура є достатньо гнучкою для розширення та відповідає специфіці NoSQL-підходу.
З точки зору UML-проєктування, наведена схема відображає компонентну діаграму системи, у межах якої кожен блок виконує окрему функцію, а стрілки показують основні напрями взаємодії між компонентами. Клієнтський інтерфейс надсилає запити до серверної частини та зовнішніх API, серверна частина взаємодіє з базою даних, а результати обробки повертаються назад до інтерфейсу користувача. Така організація забезпечує чіткий розподіл відповідальності між компонентами та полегшує подальший розвиток системи.
Перевагою обраної компонентної моделі є її модульність і придатність до масштабування. У поточній архітектурі вже передбачено інтеграцію AI-модуля на базі LangChain, який відповідає за обробку природномовних запитів користувача та формування персоналізованих рекомендацій. Завдяки відокремленню цього компонента від основної серверної логіки система може надалі розширюватися без повного перепроєктування: наприклад, аналітичного модуля або сервісу сповіщень.
Отже, проведене UML-проєктування компонентів системи дозволило визначити основні структурні елементи платформи AdoptPet, їх функції та взаємозв’язки. Побудована модель відображає логіку роботи fullstack-застосунку та створює основу для подальшої реалізації серверної, клієнтської та інтелектуальної складових системи.
[Heading2] 2.3 Проєктування бази даних та інтерфейсів.
База даних платформи AdoptPet реалізована із використанням документоорієнтованого підходу на основі MongoDB Atlas. Такий підхід дозволяє забезпечити гнучке зберігання даних, пов’язаних із тваринами, користувачами, заявками на адопцію та результатами роботи інтелектуального модуля.
Основними сутностями системи є користувачі (User), анкети тварин (Post) та заявки на адопцію (AdoptionForm). Між сутностями реалізовано логічні зв’язки, які забезпечують взаємодію користувачів із платформою та дозволяють зберігати історію поданих заявок.
Рис. 2.3. ER-діаграма бази даних платформи AdoptPet
Обґрунтування вибору MongoDB Atlas
Вибір MongoDB Atlas зумовлений особливостями предметної області та необхідністю забезпечення гнучкої роботи з напівструктурованими даними.
Основними перевагами використання MongoDB Atlas є:
гнучкість структури даних — тварини, користувачі та притулки можуть мати різні набори характеристик, тому документоорієнтована модель дозволяє зберігати записи без жорстко визначеної схеми;
швидкість розробки — BSON/JSON-структура даних легко інтегрується із серверною логікою Next.js та спрощує взаємодію між frontend і backend;
масштабованість — MongoDB Atlas підтримує горизонтальне масштабування та автоматичне розподілення навантаження;
підтримка географічних запитів — система може використовувати геоіндекси для пошуку притулків або тварин поблизу користувача;
інтеграція з Node.js та Next.js — офіційний драйвер MongoDB забезпечує ефективну роботу Server Actions та API Routes.
Використання NoSQL-підходу також є доцільним через наявність AI-модуля, який формує додаткові динамічні характеристики тварин, зокрема результати класифікації породи, опис особливостей та рекомендаційні параметри.
Під час проєктування інтерфейсу було проаналізовано існуючі платформи у сфері адопції тварин, зокрема Adopt.ua, Happy Paw та DogCat. Більшість із них використовують класичний каталоговий підхід із мінімальною інтерактивністю та відсутністю персоналізованої підтримки користувача.

[Heading2] 2.4 Вибір технологічного стеку
Вибір технологічного стеку є важливим етапом розробки програмного забезпечення, оскільки він визначає продуктивність, масштабованість, зручність підтримки та можливість подальшого розвитку системи. У межах даного проєкту було обрано сучасний стек веб-технологій, який відповідає вимогам до створення інтелектуальної платформи з високим рівнем інтерактивності та гнучкості.
[Heading3] Клієнтська частина системи
Клієнтська частина системи реалізована з використанням фреймворку Next.js 14, який базується на бібліотеці React 18. Використання Next.js дозволяє поєднати можливості серверного та клієнтського рендерингу, що позитивно впливає на продуктивність застосунку та швидкість завантаження сторінок.
Застосування App Router забезпечує більш гнучку організацію маршрутизації та дозволяє ефективно працювати з серверними компонентами. React 18 забезпечує реалізацію реактивного інтерфейсу користувача та підтримує компонентний підхід до розробки, що забезпечує швидку реакцію системи на дії користувача.
Для стилізації інтерфейсу застосовано CSS Modules, що дозволяє уникнути конфліктів стилів та забезпечує модульність коду. Також використовується бібліотека Headless UI, яка надає доступні та гнучкі UI-компоненти без прив’язки до конкретного дизайну, що дозволяє реалізувати сучасний та зручний інтерфейс користувача.
[Heading3] Backend частина
Серверна логіка реалізована у межах Next.js із використанням API Routes та Server Actions. Такий підхід дозволяє уникнути створення окремого backend-сервісу та забезпечує тісну інтеграцію між клієнтською та серверною частинами.
Використання Server Actions дозволяє реалізувати взаємодію між клієнтською та серверною частинами без створення окремого REST-сервісу, що зменшує складність архітектури та кількість мережевих викликів.
Для зберігання даних використовується MongoDB Atlas — хмарна NoSQL база даних, яка забезпечує гнучкість у роботі з напівструктурованими даними та автоматичне масштабування. Взаємодія з базою даних здійснюється через бібліотеку Mongoose, яка виступає як ODM (Object Data Modeling) та дозволяє працювати з даними у вигляді об’єктів.
[Heading3] Система автентифікації та безпеки
Для реалізації механізмів автентифікації та управління доступом використовується бібліотека Auth.js (NextAuth), яка підтримує як класичну авторизацію за логіном і паролем, так і OAuth-автентифікацію через сторонні сервіси.
З метою забезпечення безпеки даних користувачів використовується бібліотека bcryptjs, яка реалізує хешування паролів. Це дозволяє зберігати паролі у зашифрованому вигляді та захищає їх від несанкціонованого доступу.
[Heading3] Інструменти розробки та середовище
Для забезпечення якості коду та ефективної розробки використовуються сучасні інструменти:
ESLint — для автоматичного аналізу коду та виявлення помилок;
Git — для контролю версій та спільної роботи над проєктом.
Середовище розробки базується на використанні Visual Studio Code із додатковими розширеннями (ESLint, Prettier, MongoDB), що забезпечує зручність написання та форматування коду.
Для розгортання застосунку використовується платформа Vercel, яка оптимізована для роботи з Next.js та підтримує serverless-архітектуру. База даних розміщується у хмарному середовищі MongoDB Atlas.
Змінні оточення (наприклад, MONGODB_URI, AUTH_SECRET) зберігаються у файлах типу .env, що дозволяє безпечно управляти конфігурацією системи.
[Heading3] Зовнішні бібліотеки та API
У системі також використовуються додаткові бібліотеки та зовнішні API, які розширюють її функціональні можливості.
Основними бібліотеками є:
mongoose — для роботи з моделями даних;
bcryptjs — для шифрування паролів;
next-auth — для управління сесіями користувачів.
[Heading3] Технології інтелектуального модуля
Для реалізації AI-помічника та рекомендаційного функціоналу використовується бібліотека LangChain, яка забезпечує взаємодію з мовними моделями та обробку природної мови.
Інтелектуальний модуль дозволяє аналізувати текстові запити користувачів, інтерпретувати їх характеристики та формувати персоналізовані рекомендації щодо адопції тварин.
Для задач комп’ютерного зору використовуються моделі глибокого навчання, реалізовані засобами PyTorch та бібліотеки timm. Це дозволяє виконувати класифікацію порід тварин за фотографіями та автоматично доповнювати інформацію про тварину.
Рис. 2.6. Технологічний стек платформи AdoptPet
Таким чином, обраний технологічний стек забезпечує гнучкість, масштабованість та можливість інтеграції інтелектуальних модулів у платформу AdoptPet. Використання сучасних fullstack-технологій дозволяє створити продуктивний веб-застосунок із підтримкою AI-функціоналу та можливістю подальшого розвитку системи.
[Heading2] 2.5 Проєктування системи безпеки
Забезпечення інформаційної безпеки є критично важливою складовою сучасних веб-застосунків, особливо систем, що працюють із персональними даними користувачів та механізмами автентифікації. У межах платформи AdoptPet реалізовано комплексний підхід до захисту даних, який включає механізми автентифікації, авторизації, шифрування та контролю доступу.
Одним із основних елементів безпеки є захист облікових даних користувачів. Для цього використовується бібліотека bcryptjs, яка забезпечує хешування паролів перед їх збереженням у базі даних. На відміну від простого шифрування, хешування є одностороннім процесом, що унеможливлює відновлення пароля навіть у разі компрометації бази даних. Це значно підвищує рівень захисту персональної інформації.
Для реалізації механізму автентифікації використовується бібліотека Auth.js (NextAuth), яка підтримує сучасні підходи до управління користувацькими сесіями.
У системі застосовується використання JSON Web Tokens (JWT), що дозволяє безпечно передавати інформацію про користувача між клієнтом і сервером. JWT містить підписані дані про користувача та перевіряється за допомогою секретного ключа, що забезпечує цілісність і достовірність токена.
Використання stateless-підходу дозволяє зменшити навантаження на сервер та спрощує горизонтальне масштабування системи.
Для спрощення процесу входу в систему та підвищення зручності користувачів реалізовано підтримку протоколу OAuth 2.0. Це дозволяє користувачам авторизуватися через сторонні сервіси, зокрема Google.
Використання OAuth зменшує необхідність створення окремих облікових записів і підвищує рівень безпеки, оскільки обробка облікових даних делегується надійним зовнішнім провайдерам.
Для забезпечення безпеки даних, що зберігаються у MongoDB Atlas, використовуються вбудовані механізми захисту, зокрема:
обмеження доступу до бази даних через IP-фільтрацію;
використання захищених рядків підключення;
автентифікація на рівні користувачів бази даних;
резервне копіювання даних.
Це дозволяє мінімізувати ризик несанкціонованого доступу та втрати інформації.
У системі реалізовано модель контролю доступу на основі ролей (RBAC – Role-Based Access Control). Користувачам призначаються ролі, які визначають їх права доступу до функціоналу системи.
Адміністративні права визначаються роллю користувача у системі.
Для звичайних користувачів доступ до адміністративного функціоналу обмежений, що забезпечує розмежування прав і підвищує безпеку системи.
Доступ до серверних маршрутів контролюється через механізми автентифікації. Закриті API-маршрути доступні лише для авторизованих користувачів, що перевіряється за допомогою JWT або сесій, створених через Auth.js.
Це дозволяє запобігти несанкціонованим запитам та захистити критичні функції системи, такі як подання заявок або редагування даних.
Рис. 2.7. Діаграма послідовності
Таким чином, реалізована система безпеки забезпечує захист персональних даних користувачів, контроль доступу до функціоналу платформи та безпечну взаємодію між клієнтською і серверною частинами системи. Використання сучасних механізмів автентифікації та захисту даних дозволяє підвищити надійність і масштабованість веб-застосунку AdoptPet.
[Heading2] 2.6 Організація процесу розгортання (CI/CD та Контейнеризація).
Організація процесу розгортання є важливою складовою сучасної розробки програмного забезпечення, оскільки забезпечує стабільність роботи системи, повторюваність середовища та можливість швидкого впровадження змін. У межах платформи AdoptPet для цього використовуються підходи контейнеризації та безперервної інтеграції і розгортання (CI/CD).
Для забезпечення цілісності та незалежності середовища виконання використовується технологія Docker, яка дозволяє упаковувати застосунок разом із усіма його залежностями у вигляді контейнерів.
У межах даної системи застосунок логічно розділено на кілька основних компонентів, кожен із яких реалізується як окремий контейнер:
Frontend/Backend (Next.js fullstack) – основний веб-застосунок, який відповідає за інтерфейс користувача, серверну логіку та взаємодію з базою даних;
База даних (MongoDB Atlas) – використовується як хмарний сервіс, однак у випадку локального розгортання може бути винесена в окремий контейнер;
Інтелектуальний модуль (ML / LangChain) – окремий сервіс, який виконує обробку запитів користувача, аналіз даних та формування рекомендацій.
Такий підхід дозволяє ізолювати компоненти системи, спростити їх розгортання та забезпечити незалежність середовища виконання. Кожен контейнер має власні залежності та конфігурацію, що виключає конфлікти між компонентами.
Для оркестрації контейнерів використовується Docker Compose, який дозволяє запускати всі компоненти системи одночасно як єдиний застосунок.
Для автоматизації процесу розробки та розгортання застосунку використовується підхід CI/CD (Continuous Integration / Continuous Deployment).
Безперервна інтеграція (CI) передбачає автоматичну перевірку коду при кожному оновленні репозиторію. У процесі CI виконуються такі етапи:
перевірка якості коду (ESLint);
збірка застосунку;
запуск автоматизованих тестів та перевірка коректності збірки застосунку;
перевірка залежностей.
Це дозволяє своєчасно виявляти помилки та підтримувати стабільність проєкту.
Безперервне розгортання (CD) забезпечує автоматичне оновлення застосунку після внесення змін. У даному проєкті розгортання frontend/backend частини здійснюється за допомогою платформи Vercel, яка інтегрується з GitHub та автоматично деплоїть застосунок при кожному оновленні гілки.
Інтелектуальний модуль може розгортатися окремо (наприклад, як окремий контейнер або хмарний сервіс), що дозволяє масштабувати його незалежно від основної системи.
Застосування контейнеризації та CI/CD у межах платформи AdoptPet забезпечує такі переваги:
повторюваність середовища – однаковість середовищ розробки, тестування та експлуатації системи;
швидкість розгортання – автоматичний запуск системи без ручного налаштування;
масштабованість – можливість окремого масштабування компонентів;
надійність – зменшення кількості помилок, пов’язаних із конфігурацією;
гнучкість – можливість легко додавати нові сервіси (наприклад, ML-модулі).

[Heading1] РОЗДІЛ 3. РЕАЛІЗАЦІЯ ПРОГРАМНОГО КОМПЛЕКСУ
[Heading2] 3.1 Реалізація серверної частини (Backend)
Серверна частина платформи AdoptPet реалізована у межах fullstack-підходу на основі фреймворку Next.js, що дозволяє поєднати клієнтську та серверну логіку в одному середовищі. Такий підхід забезпечує ефективну обробку запитів, виконання бізнес-логіки та взаємодію з базою даних без необхідності створення окремого серверного застосунку.
Структура серверної частини організована відповідно до сучасних підходів до розробки веб-застосунків і включає рівні обробки запитів, роботи з даними та механізми автентифікації. Основними елементами є API Routes та Server Actions, які виконують роль контролерів, забезпечуючи обробку HTTP-запитів і взаємодію із системою з боку клієнта.
Рис. 3.1. Структура директорій backend-частини AdoptPet
Підключення до бази даних реалізовано з використанням хмарного сервісу MongoDB Atlas. Конфігурація з’єднання здійснюється через змінні оточення, зокрема параметр MONGODB_URI, який містить усі необхідні дані для доступу до бази. Такий підхід дозволяє забезпечити безпечне зберігання конфіденційної інформації та спростити процес розгортання застосунку у різних середовищах.
Рис. 3.2. MongoDB Atlas Колекції для AdoptPET
Функції обробки запитів у системі реалізовані за допомогою API Routes та Server Actions. API Routes, розташовані у директорії app/api, забезпечують обробку стандартних HTTP-запитів, таких як отримання, створення або видалення даних. Водночас Server Actions дозволяють виконувати серверну логіку безпосередньо з компонентів, що значно зменшує кількість проміжних запитів і спрощує архітектуру. Контролери приймають запити від клієнта, здійснюють валідацію даних, викликають необхідну логіку та повертають результат у форматі JSON.
Робота з даними реалізована за допомогою бібліотеки Mongoose, яка виступає як об’єктно-документна модель (ODM) для MongoDB. У межах проєкту визначено основні моделі даних, що відповідають колекціям pets, users та applications. Взаємодія з базою даних здійснюється через окремі функції, які виконують операції створення, читання, оновлення та видалення записів. Такий підхід фактично реалізує рівень репозиторіїв, що дозволяє ізолювати логіку роботи з даними та спростити подальшу підтримку системи.
Для забезпечення безпеки доступу до системи використовується бібліотека Auth.js (NextAuth), яка реалізує механізми автентифікації та управління сесіями. У системі застосовується перевірка користувача за логіном і паролем із використанням Credentials-провайдера, при цьому паролі зберігаються у вигляді хешів за допомогою bcryptjs. Після успішної автентифікації формується JWT-токен, який містить ідентифікатор користувача та його роль. Ці дані використовуються для формування сесії та контролю доступу до функціоналу системи. Додатковий захист маршрутів реалізовано через middleware, який перевіряє наявність авторизації перед наданням доступу до захищених ресурсів.
Для документування та тестування серверної частини використовується Swagger (OpenAPI), який дозволяє описати структуру API, визначити формати запитів і відповідей та забезпечити зручний інтерфейс для тестування. Це спрощує процес розробки, особливо при інтеграції із зовнішніми сервісами, зокрема інтелектуальним модулем.

Таким чином, використання Swagger дозволяє спростити процес тестування та документування серверної частини платформи AdoptPet, а також підвищує зручність подальшої підтримки й розвитку системи.

Клієнтська частина платформи AdoptPet реалізована з використанням фреймворку Next.js 14 на базі бібліотеки React 18. Такий підхід дозволяє створити сучасний, інтерактивний та продуктивний інтерфейс користувача, який забезпечує зручну взаємодію із системою та ефективне оновлення та рендеринг інтерфейсу.
Архітектура клієнтської частини побудована на основі компонентного підходу, що є характерним для React-застосунків. Інтерфейс складається з набору незалежних компонентів, кожен із яких відповідає за окрему частину функціоналу. Це дозволяє повторно використовувати код, спрощує підтримку та забезпечує гнучкість при розширенні системи.
Рис. 3.4. Структура директорій клієнтської частини AdoptPet
Як показано на рисунку 3.4, структура клієнтської частини організована за модульним принципом, де компоненти згруповані відповідно до їх функціонального призначення.
Одним із ключових елементів інтерфейсу є навігаційна панель (Navbar), яка забезпечує доступ до основних розділів платформи та змінюється залежно від стану авторизації користувача. У компоненті використовується серверна функція auth(), що дозволяє отримати інформацію про поточну сесію та передати її до дочірніх компонентів для відображення відповідного функціоналу.
Реалізація інтерфейсу базується на принципах UI/UX-дизайну, що передбачають простоту, зрозумілість та доступність. Основна увага приділяється зручності користувача, швидкому доступу до інформації та мінімізації кількості дій, необхідних для виконання основних сценаріїв, таких як пошук тварини або подання заявки. Використання CSS Modules забезпечує ізоляцію стилів та підтримує модульність компонентів, що дозволяє уникнути конфліктів і спрощує масштабування інтерфейсу.
Для підвищення адаптивності інтерфейсу застосовано responsive-підхід, що забезпечує коректне відображення платформи на різних типах пристроїв, зокрема смартфонах, планшетах та персональних комп’ютерах.
Взаємодія клієнтської частини із серверною реалізована через Server Actions, що дозволяє спростити обмін даними між компонентами та сервером без необхідності створення окремого шару REST-запитів для частини операцій.
Управління станом у застосунку реалізовано з використанням вбудованих механізмів React, зокрема useState та Context API. Такий підхід дозволяє забезпечити реактивне оновлення інтерфейсу при зміні даних і відповідає патерну Observer, коли компоненти автоматично реагують на зміни стану. На відміну від більш складних рішень, таких як Redux або Zustand, обраний підхід є достатнім для поточного масштабу системи та дозволяє зберегти простоту реалізації.
Використання Server Actions для виконання запитів відповідає патерну Command, оскільки кожна дія інкапсулює конкретну операцію (наприклад, створення або видалення запису) та виконується незалежно від інших частин системи. Це дозволяє розділити відповідальність між компонентами та зробити код більш структурованим.
Таким чином, клієнтська частина платформи AdoptPet реалізована із використанням сучасних підходів до розробки веб-інтерфейсів. Компонентна архітектура, інтеграція із серверною логікою через Server Actions та ефективне управління станом забезпечують високу продуктивність, зручність використання та можливість подальшого розвитку системи.
[Heading2] 3.3 Взаємодія з модулем машинного навчання через API
Інтелектуальний модуль у системі AdoptPet реалізований як окремий сервіс, який виконує обробку даних користувача та формує персоналізовані рекомендації щодо вибору тварини. З технічної точки зору цей модуль реалізовано на мові Python із використанням сучасних бібліотек машинного навчання та інтегровано у веб-застосунок через API.
Для реалізації API інтелектуального модуля використовується фреймворк FastAPI, який забезпечує високу продуктивність, асинхронну обробку запитів та автоматичну генерацію документації OpenAPI (Swagger).
Взаємодія між основною серверною частиною застосунку (Next.js) та ML-модулем здійснюється за принципом клієнт-серверної взаємодії через HTTP-запити. Backend виступає у ролі клієнта, який надсилає запит до Python-сервісу, передаючи необхідні параметри для аналізу, після чого отримує результат у форматі JSON.
Процес взаємодії починається з отримання даних від користувача. До таких параметрів належать тип житла, рівень активності користувача, наявність дітей, досвід утримання тварин та інші характеристики. Після цього серверна частина формує структурований запит і надсилає його до ML-сервісу через REST API.
На стороні Python-сервісу відбувається обробка отриманих даних. На стороні Python-сервісу виконується аналіз отриманих даних із використанням моделей машинного навчання та алгоритмів рекомендаційної системи. Після виконання обчислень сервіс формує відповідь у форматі JSON, яка містить список рекомендованих тварин та їх характеристик.
Отриманий результат передається назад на сервер Next.js, де відбувається його додаткова обробка та інтеграція з даними з бази MongoDB. Наприклад, за ідентифікаторами тварин можуть бути отримані повні анкети, після чого сформований список рекомендацій передається на клієнтську частину для відображення користувачу.Важливою перевагою такого підходу є розділення відповідальності між компонентами системи. ML-модуль працює як незалежний сервіс, що дозволяє масштабувати його окремо від основного застосунку, оновлювати моделі без змін у backend-частині та використовувати різні технології для реалізації.
Крім того, використання API забезпечує гнучкість інтеграції та дозволяє у майбутньому підключати додаткові інтелектуальні функції, такі як класифікація порід тварин за зображенням або аналіз текстових запитів користувача.

[Heading2] 4.3 Побудова та навчання прогнозних моделей
На початковому етапі розробки системи було необхідно визначити, яку архітектуру глибокої нейронної мережі доцільно використовувати для задачі класифікації порід тварин. Серед найбільш популярних рішень для комп’ютерного зору розглядалися такі архітектури, як VGG, ResNet, Vision Transformers та EfficientNet. Кожна з них має свої переваги й обмеження: наприклад, моделі сімейства VGG є простими для реалізації, але містять надмірно велику кількість параметрів; Vision Transformers демонструють високу точність, але потребують дуже великих датасетів і стабільного обчислювального середовища; ResNet вважається надійною «класичною» архітектурою, придатною для складних задач розпізнавання.
Щоб отримати базове уявлення про те, як класичні згорткові мережі поводяться на датасеті порід тварин, було виконано експериментальне навчання моделі ResNet-18. Результати цього експерименту показали, що модель поступово покращує свої показники, але робить це доволі повільно. За 15 епох навчання точність Top-1 на валідаційній вибірці зросла приблизно до 0.67, тоді як Top-5 — до 0.93. Характер графіків свідчить, що ResNet-18 досяг свого майже максимального потенціалу: функція втрат зменшувалася дуже повільно, а валідаційна точність стабілізувалась на рівні, який недостатній для практичної системи, націленої на високу точність класифікації великої кількості порід. Крім того, ResNet-18 має обмежену глибину і працює з меншою деталізацією зображень, що для тонких міжкласових відмінностей є суттєвим недоліком.

Було обрано EfficientNet-B3, яка забезпечує значно кращу якість упізнавання при порівнянній кількості параметрів. Завдяки принципу комбінованого масштабування (глибина, ширина та роздільна здатність збільшуються пропорційно), EfficientNet-B3 дозволяє моделі опрацьовувати високодеталізовані зображення та формувати набагато виразніші ознаки. Під час навчання ця архітектура продемонструвала значно вищу валідаційну точність (понад 0.84 Top-1), швидше сходження та нижче значення функції втрат у порівнянні з ResNet-18.
Рис. 4.5. Структура частини проекту, що відповідає за підготовку та аугментація даних
Підготовка даних реалізована в модулі datamodule.py за допомогою класу BreedDataModule, який наслідує pl.LightningDataModule, повний код у Додатку 4. Датасет організований у вигляді поділу на три підмножини (train, val, test), кожна з яких являє собою каталог з підкаталогами за назвами класів (порід). Для роботи використовується стандартний клас torchvision.datasets.ImageFolder, що автоматично будує відповідність «назва папки → індекс класу».
У класі BreedDataModule визначено шлях до даних, розмір батчу, кількість потоків завантаження, а також розмір зображень, до якого вони приводяться. Метод setup() створює окремі екземпляри ImageFolder для тренувальної, валідаційної та тестової вибірок, застосовуючи відповідні трансформації.
Самі трансформації описані в модулі transforms.py у функції build_transforms(image_size: int), повний код у Додатку 5. Для тренувальної вибірки передбачено аугментації, що покращують здатність моделі до узагальнення: масштабування до максимальної сторони, доповнення до квадрату, випадкове масштабоване кадрування, горизонтальне віддзеркалення, невеликі повороти, а також зміну яскравості, контрасту, насиченості та відтінку. Після цього виконується нормалізація до статистики ImageNet та перетворення в тензор.
Валідаційні й тестові дані обробляються більш консервативно: зображення лише масштабуються, доповнюються до квадрату, центровано кадруються та нормалізуються без випадкових спотворень. Це забезпечує стабільність метрик на перевірочних вибірках.
Для зручної інтеграції Albumentations із PyTorch використано спеціальний обгортаючий клас AlbumentationsTransform, що приймає на вхід або PIL.Image, або масив NumPy, застосовує до нього композицію перетворень, а на виході повертає PyTorch-тензор.
Як базову архітектуру обрано попередньо натреновану модель сімейства EfficientNet, що реалізується через бібліотеку timm у модулі efficientnet.py, повний код у Додатку 6. Конкретна версія моделі задається параметром model_name (за замовчуванням – efficientnet_b3). Використання попередньо натренованих ваг дозволяє застосувати підхід трансферного навчання: мережа вже володіє узагальненими ознаками для природних зображень, а подальше донавчання адаптує її під конкретне завдання класифікації порід.
Клас EfficientNetClassifier успадковує pl.LightningModule і інкапсулює всю логіку моделі: створення базової архітектури, вибір функції втрат, налаштування оптимізатора, а також визначення кроків навчання, валідації та тестування. Кількість вихідних нейронів в останньому шарі відповідає кількості класів у вибраному датасеті, яка передається як параметр num_classes.
Особливістю реалізації є механізм часткового «заморожування» ваг. На початкових етапах навчання ваги базової частини мережі (backbone)  фіксуються, а оновлюється лише фінальний класифікаційний шар. Це задається методом _freeze_backbone(), який дозволяє зменшити ризик руйнування вже корисних ознак. Починаючи з епохи unfreeze_epoch, вся модель «розморожується» у методі _unfreeze_backbone(), і починається тонке донавчання всієї архітектури.
Функція втрат динамічно обирається залежно від використання технік Mixup/CutMix. Якщо відповідні параметри mixup_alpha або cutmix_alpha задані, то модуль використовує SoftTargetCrossEntropy з бібліотеки timm та застосовує змішування зображень і міток через об’єкт Mixup. В іншому випадку використовується звичайна CrossEntropyLoss з можливістю згладжування міток (label_smoothing). Для оцінювання якості моделі використовуються метрики точності top-1 і top-k на основі бібліотеки torchmetrics.

На рисунку 4.12 подано динаміку зростання точності Top-1 у процесі навчання. Усі три моделі демонструють швидкий приріст точності в перші етапи навчання, причому темпи росту залишаються схожими: найбільший прогрес спостерігається до шостої епохи, після чого точність поступово стабілізується.

Модель, натренована на Stanford Dogs, демонструє також високий рівень точності (понад 0.87), але досягає його значно пізніше — на тринадцятій епосі. Для датасету Kaggle Dog Breed пікова точність виявляється нижчою (приблизно 0.85). Серед причин — найвищий рівень варіативності зображень та найбільша кількість класів. Попри це, модель зберігає достатньо високу точність, що свідчить про ефективність архітектури та здатність моделі адаптуватися до складних даних.
Важливо зазначити, що жодна з моделей не демонструє істотного перенавчання. Хоча тренувальна точність у кінцевих епохах наближається до 0.99, валідаційна точність не спадає різко після пікових значень. Тобто модель продовжує узагальнювати інформацію належним чином, що підтверджує правильний вибір аугментацій, початкового навчального режиму та стратегії поступового розморожування.
[Heading2] 4.6 Інтеграція AI-помічника та генерації характеристик
Окрім модуля комп’ютерного зору для визначення породи тварини, у платформі AdoptPet реалізовано додатковий інтелектуальний функціонал на основі мовних моделей. Його призначення полягає у підтримці користувача під час вибору тварини та автоматизації формування описів для анкет тварин.
Рис. 4.13. Архітектура AI-модуля платформи AdoptPet
Інтеграція AI-функціоналу реалізована у модулі agentChain.js, де використовується бібліотека LangChain та модель gpt-4o-mini через клас ChatOpenAI. У цьому модулі визначено дві основні логіки роботи: генерація опису та характеристик тварини для картки та рекомендація тварин користувачу на основі його текстового запиту.
Перший напрям — генерація опису та характеристик тварини для картки. Для цього використовується структура PetDescriptionSchema, яка задає очікуваний формат відповіді моделі: короткий заголовок, основний текст, теги характеру, опис ідеального власника та додаткові потреби тварини. Такий підхід дозволяє отримувати не довільний текст, а структурований результат, який може бути використаний у картці тварини.
Для генерації опису застосовується спеціальний prompt, у якому модель отримує характеристики тварини: ім’я, тип, породу, вік, розмір, стать, місто та поточний опис. У системному повідомленні також задано обмеження: не вигадувати медичні факти, не гарантувати характер тварини, формувати теплий, доброзичливий і чесний текст українською мовою. Це важливо для предметної області, оскільки інформація про тварину повинна бути корисною, але не вводити користувача в оману.
Функція generatePetDescription приймає дані тварини, передає їх у LangChain-послідовність і повертає структурований опис. Якщо певне поле не заповнене, система використовує значення “не вказано” або “відсутній”, що дозволяє уникнути помилок під час генерації тексту.
На рівні API генерація опису реалізована через маршрут POST /api/agent/description. Маршрут отримує дані з тіла запиту, викликає функцію generatePetDescription і повертає результат у форматі JSON. У разі помилки сервер повертає відповідь зі статусом 500 і повідомленням про неможливість згенерувати опис.
Другий напрям — AI-помічник для користувача. Його задача полягає у персоналізованому підборі тварин для адопції. Користувач може описати свої побажання природною мовою, наприклад умови проживання, бажаний характер тварини, розмір або рівень активності. Після цього AI-помічник аналізує запит і порівнює його з доступними тваринами в каталозі.
Для цього у agentChain.js визначено окремий prompt, який задає роль моделі як віртуального консультанта платформи AdoptPet. У правилах зазначено, що модель повинна відповідати українською мовою, рекомендувати лише тих тварин, які реально є у списку, не вигадувати неіснуючих тварин, пояснювати причини рекомендації та вставляти посилання у форматі Markdown.
Функція recommendPetsForClient спочатку підключається до бази даних, після чого отримує з колекції Post лише доступних для адопції тварин зі статусом available. Для оптимізації обробки вибираються тільки необхідні поля: назва, slug, тип, порода, вік, розмір, стать, місто, опис і статус. Кількість записів обмежується 20, що дозволяє зменшити розмір контексту, який передається мовній моделі.
Після отримання даних система формує текстовий список доступних тварин, де для кожної анкети вказуються основні характеристики та внутрішнє посилання на сторінку /catalog/{slug}. Цей список разом із запитом користувача передається у мовну модель, яка формує відповідь із рекомендаціями.
На рівні API AI-помічник реалізований через маршрут POST /api/agent/chat. Маршрут отримує повідомлення користувача, перевіряє, чи воно не є порожнім, викликає функцію recommendPetsForClient і повертає відповідь у форматі JSON. Якщо повідомлення відсутнє, сервер повертає статус 400, а у випадку внутрішньої помилки — статус 500.
Таким чином, інтелектуальний модуль AdoptPet складається не лише з ML-класифікатора породи, а й із LLM-компонентів, які виконують дві прикладні функції: підтримку користувача під час вибору тварини та автоматизацію створення якісних описів для анкет. Така інтеграція підвищує зручність роботи з платформою, зменшує ручне навантаження на адміністратора та робить процес адопції більш персоналізованим.
[Heading2] Висновки до розділу
У межах четвертого розділу було проведено дослідження, розробку та практичну реалізацію інтелектуального модуля платформи AdoptPet, який поєднує технології комп’ютерного зору та сучасні мовні моделі для підтримки процесу адопції тварин.
На першому етапі виконано збір і підготовку даних для задачі класифікації порід тварин. Для навчання моделей використано три відкриті датасети: Stanford Dogs, Oxford-IIIT Pet та Kaggle Dog Breed Identification. Проведено уніфікацію структури даних, стандартизацію форматів зображень та реалізовано механізми попередньої обробки й аугментації, що дозволило забезпечити сумісність даних із фреймворком PyTorch та підвищити здатність моделей до узагальнення.
У процесі дослідження було виконано порівняння різних архітектур глибоких нейронних мереж. Експеримент із ResNet-18 показав обмежену ефективність для задач fine-grained класифікації великої кількості схожих порід. У результаті для основної системи було обрано архітектуру EfficientNet-B3, яка продемонструвала вищу точність, стабільніше навчання та кращу здатність працювати зі складними високодеталізованими зображеннями.
Реалізовано повний цикл навчання моделі із використанням transfer learning, механізму поступового розморожування ваг, а також сучасних технік регуляризації та аугментації. Для оцінювання якості роботи моделей проведено аналіз матриць помилок, precision, recall та F1-міри на всіх трьох датасетах. Отримані результати підтвердили високу ефективність обраної архітектури: моделі демонструють стабільні показники точності та коректно узагальнюють інформацію без суттєвого перенавчання.
Окрему увагу приділено інтеграції мовних моделей у платформу. У системі реалізовано AI-помічника для персоналізованого підбору тварин, а також модуль автоматичної генерації описів і характеристик для карток тварин. Для цього використано бібліотеку LangChain та модель GPT-4o-mini. Розроблений підхід дозволив автоматизувати частину роботи адміністратора, забезпечити структуровану генерацію тексту та зробити взаємодію користувача з платформою більш природною та зручною.
У результаті було сформовано комплексний інтелектуальний модуль, який поєднує ML-класифікацію, обробку природної мови та веб-інтеграцію в межах єдиної системи AdoptPet. Запропоноване рішення підвищує функціональність платформи, покращує якість взаємодії користувачів із сервісом та створює основу для подальшого розвитку AI-компонентів у системах адопції тварин.

[Heading2] 5.3 Розгортання системи в хмарному середовищі
Розгортання платформи AdoptPet передбачає запуск кількох взаємопов’язаних компонентів: основного веб-застосунку на Next.js, ML-сервісу на FastAPI, хмарної бази даних MongoDB Atlas та зовнішніх API для роботи AI-помічника. Така структура дозволяє відокремити логіку веб-платформи від обчислювально складного модуля машинного навчання та забезпечити гнучке масштабування окремих частин системи.
Основний веб-застосунок виконує функції frontend- та backend-рівня. Він відповідає за відображення інтерфейсу користувача, маршрутизацію, авторизацію, роботу з каталогом тварин, обробку заявок на адопцію та взаємодію з базою даних. ML-сервіс реалізований окремо на FastAPI та використовується для класифікації породи тварини за зображенням. Комунікація між Next.js-застосунком і ML-сервісом виконується через REST API у форматі JSON.
Для організації запуску системи як єдиного програмного комплексу було підготовлено схему контейнеризації на основі Docker Compose. Docker Compose дозволяє описати всі сервіси системи в одному конфігураційному файлі та запускати їх однією командою. У межах AdoptPet до складу контейнерного середовища входять два основні сервіси: web, який відповідає за Next.js-застосунок, та ml-service, який запускає FastAPI-сервер з моделлю машинного навчання.
Рис. 5.9. Діаграма розгортання AdoptPet
Процес розгортання системи складається з кількох етапів. Спочатку виконується збірка Docker-образів для Next.js-застосунку та FastAPI-сервісу. Після цього Docker Compose створює внутрішню мережу, запускає ML-сервіс, а потім основний веб-застосунок. Під час запуску Next.js отримує змінні середовища, серед яких MONGODB_URI, AUTH_SECRET, OPENAI_API_KEY та ML_SERVICE_URL.
Після запуску користувач взаємодіє з платформою через браузер. Запити до каталогу, авторизації, адміністративної панелі та заявок обробляються Next.js-застосунком. Якщо користувач або адміністратор запускає визначення породи за зображенням, Next.js надсилає HTTP-запит до FastAPI-сервісу. ML-сервіс виконує попередню обробку зображення, завантажує модель EfficientNet-B3, формує прогноз і повертає результат у форматі JSON.
Після запуску користувач взаємодіє з платформою через браузер. Запити до каталогу, авторизації, адміністративної панелі та заявок обробляються Next.js-застосунком. Якщо користувач або адміністратор запускає визначення породи за зображенням, Next.js надсилає HTTP-запит до FastAPI-сервісу. ML-сервіс виконує попередню обробку зображення, завантажує модель EfficientNet-B3, формує прогноз і повертає результат у форматі JSON.
Контейнеризація забезпечує повторюваність середовища виконання. Це означає, що застосунок може бути запущений однаково на локальному комп’ютері, тестовому сервері або хмарній інфраструктурі. Усі залежності, версії бібліотек і параметри запуску фіксуються в Dockerfile та docker-compose.yml, що зменшує ризик помилок, пов’язаних із відмінностями середовища.
Для хмарного розгортання можливі два сценарії. Перший сценарій передбачає розміщення Next.js-застосунку на Vercel, а ML-сервісу — на окремому cloud-сервері або контейнерній платформі. Другий сценарій передбачає запуск усіх контейнерів на одному cloud-host через Docker Compose. У межах даної роботи доцільним є другий варіант як інженерна схема фінального запуску повного комплексу, оскільки він дозволяє одночасно підняти веб-застосунок і ML-сервіс та перевірити їхню взаємодію в єдиному середовищі.
Перевагами запропонованої схеми розгортання є: ізоляція Next.js-застосунку та ML-сервісу; можливість незалежного оновлення ML-моделі; повторюваність середовища запуску; спрощення переходу від локального тестування до хмарного розгортання; можливість масштабування окремих компонентів системи.
Таким чином, розгортання AdoptPet на основі Docker Compose дозволяє представити систему як єдиний програмний комплекс, у якому frontend/backend-рівень, ML-сервіс, база даних та зовнішні API працюють у зв’язці. Такий підхід підвищує керованість системи, спрощує її підтримку та створює основу для подальшого масштабування платформи.

import { Post } from "@/lib/models";
import { connectToDb } from "@/lib/utils";
import { NextResponse } from "next/server";
export const GET = async (request) => {
try {
connectToDb();
const { searchParams } = new URL(request.url);
const search = searchParams.get("search");
const type = searchParams.get("type");
const age = searchParams.get("age");
const size = searchParams.get("size");
let query = {};
if (search) {
query.$or = [
{ title: { $regex: search, $options: "i" } },
{ desc: { $regex: search, $options: "i" } }
];
}
if (type) {
query.type = type;
}
if (age) {
query.ageGroups = age;
}
if (size) {
query.sizes = size;
}
const posts = await Post.find(query);
return NextResponse.json(posts);
} catch (err) {
console.log(err);
throw new Error("Не вдалося отримати дописи!");
}
};

from typing import Tuple
import albumentations as A
from albumentations.pytorch import ToTensorV2
IMAGENET_MEAN = (0.485, 0.456, 0.406)
IMAGENET_STD = (0.229, 0.224, 0.225)
def build_transforms(image_size: int) -> Tuple[A.Compose, A.Compose, A.Compose]:
"""Створює train/val/test трансформації Albumentations."""
train_tf = A.Compose(
[
A.LongestMaxSize(max_size=image_size),
A.PadIfNeeded(image_size, image_size, border_mode=0),
A.RandomResizedCrop(size=(image_size, image_size), scale=(0.9, 1.0)),
A.HorizontalFlip(p=0.5),
A.Rotate(limit=10, p=0.5),
A.ColorJitter(
brightness=0.15, contrast=0.15, saturation=0.15, hue=0.05, p=0.5
),
A.Normalize(mean=IMAGENET_MEAN, std=IMAGENET_STD),
ToTensorV2(),
]
)
eval_tf = A.Compose(
[
A.LongestMaxSize(max_size=image_size),
A.PadIfNeeded(image_size, image_size, border_mode=0),
A.CenterCrop(image_size, image_size),
A.Normalize(mean=IMAGENET_MEAN, std=IMAGENET_STD),
ToTensorV2(),
]
)
# test = та сама, що й val
test_tf = eval_tf
return train_tf, eval_tf, test_tf

from typing import Any, Optional
import pytorch_lightning as pl
import timm
import torch
import torchmetrics
from timm.data.mixup import Mixup
from timm.loss import SoftTargetCrossEntropy
class EfficientNetClassifier(pl.LightningModule):
def __init__(
self,
num_classes: int,
model_name: str = "efficientnet_b3",
learning_rate: float = 1e-4,
weight_decay: float = 1e-4,
unfreeze_epoch: int = 5,
label_smoothing: float = 0.0,
mixup_alpha: Optional[float] = None,
cutmix_alpha: Optional[float] = None,
top_k: int = 5,
) -> None:
super().__init__()
self.save_hyperparameters()
self.model = timm.create_model(model_name, pretrained=True, num_classes=num_classes)
self.learning_rate = learning_rate
self.weight_decay = weight_decay
self.unfreeze_epoch = unfreeze_epoch
self.top_k = top_k
if mixup_alpha or cutmix_alpha:
self.mixup_fn: Optional[Mixup] = Mixup(
mixup_alpha=mixup_alpha or 0.0,
cutmix_alpha=cutmix_alpha or 0.0,
num_classes=num_classes,
)
self.criterion = SoftTargetCrossEntropy()
else:
self.mixup_fn = None
self.criterion = torch.nn.CrossEntropyLoss(label_smoothing=label_smoothing)
self.train_acc = torchmetrics.Accuracy(task="multiclass", num_classes=num_classes, top_k=1)
self.val_acc = torchmetrics.Accuracy(task="multiclass", num_classes=num_classes, top_k=1)
self.val_topk = torchmetrics.Accuracy(task="multiclass", num_classes=num_classes, top_k=top_k)
self._freeze_backbone()
def forward(self, x: torch.Tensor) -> torch.Tensor:  # type: ignore[override]
return self.model(x)
def training_step(self, batch: Any, batch_idx: int) -> torch.Tensor:  # type: ignore[override]
images, targets = batch
if self.mixup_fn is not None:
images, targets = self.mixup_fn(images, targets)
logits = self.forward(images)
loss = self.criterion(logits, targets)
self.log("train_loss", loss, on_step=True, on_epoch=True, prog_bar=True)
if targets.ndim == 1:
acc = self.train_acc(logits, targets)
self.log("train_acc", acc, on_step=False, on_epoch=True, prog_bar=True)
return loss
def validation_step(self, batch: Any, batch_idx: int) -> None:  # type: ignore[override]
images, targets = batch
logits = self.forward(images)
loss = self.criterion(logits, targets)
acc1 = self.val_acc(logits, targets)
acck = self.val_topk(logits, targets)
self.log("val_loss", loss, prog_bar=True, on_epoch=True, sync_dist=True)
self.log("val_acc1", acc1, prog_bar=True, on_epoch=True, sync_dist=True)
self.log(
f"val_acc{self.top_k}",
acck,
prog_bar=False,
on_epoch=True,
sync_dist=True,
)
def test_step(self, batch: Any, batch_idx: int) -> None:  # type: ignore[override]
images, targets = batch
logits = self.forward(images)
acc1 = self.val_acc(logits, targets)
acck = self.val_topk(logits, targets)
self.log("test_acc1", acc1, prog_bar=True, on_epoch=True, sync_dist=True)
self.log(
f"test_acc{self.top_k}", acck, prog_bar=True, on_epoch=True, sync_dist=True
)
def configure_optimizers(self):  # type: ignore[override]
optimizer = torch.optim.AdamW(
self.parameters(), lr=self.learning_rate, weight_decay=self.weight_decay
)
scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(optimizer, T_max=self.trainer.max_epochs)
return {
"optimizer": optimizer,
"lr_scheduler": scheduler,
"monitor": "val_loss",
}
def on_train_epoch_start(self) -> None:  # type: ignore[override]
if self.unfreeze_epoch and self.current_epoch == self.unfreeze_epoch:
self._unfreeze_backbone()
def _freeze_backbone(self) -> None:
classifier = self.model.get_classifier()
classifier_param_ids = {id(p) for p in classifier.parameters()} if classifier else set()
for param in self.model.parameters():
if id(param) in classifier_param_ids:
param.requires_grad = True
else:
param.requires_grad = self.unfreeze_epoch == 0
